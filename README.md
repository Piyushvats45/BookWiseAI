# BookWise AI

Upload your own PDFs (books, papers, notes, docs) and ask questions about them. Answers are generated by an LLM from the passages retrieved out of *your* document, and every answer cites the book and page it came from.

**Stack:** Java 21 · Spring Boot 4 · Spring AI 2 · PostgreSQL + pgvector · React 19 · Vite · Tailwind CSS 4

## How it works

```
Upload PDF ──► validate (header, size, pages, not encrypted, parseable)
           ──► store file + book row (status PROCESSING), return 202
           ──► async: extract text page by page (PDFBox)
           ──► split each page into ~500-token chunks (TokenTextSplitter)
           ──► embed chunks (OpenAI text-embedding-3-small, 1536 dims)
           ──► store in pgvector with metadata {user_id, book_id, book_title, page_number}
           ──► status READY

Ask question ──► embed question
             ──► similarity search in pgvector (cosine, topK 6, threshold 0.25),
                 filtered by user_id AND book_id
             ──► numbered excerpts + recent chat history ──► LLM
             ──► answer in Markdown with [n] markers
             ──► citations = the excerpts the answer actually referenced (title, page, snippet)
```

Design decisions worth knowing:

- **Chunks never cross pages**, so every citation page number is exact. The trade-off is no overlap between chunks.
- **Tenant isolation:** every vector search is filtered by `user_id` as well as `book_id`, and all book/chat lookups are scoped by the JWT subject. Another user's book returns 404.
- **The `vector_store` table is created by Flyway** (`V2__vector_store.sql`), not by Spring AI, so dimensions and indexes are explicit. If you change the embedding model, change the dimension in `V2` (or add a migration) *and* `EMBEDDING_DIMENSIONS`, and re-index your books.
- **Prompt-injection hygiene:** the system prompt tells the model to treat excerpts as untrusted data, and prompts are passed as messages (not templates) so `{braces}` in a book can't break rendering.
- **JWT auth** uses Spring Security's resource server with an HS256 secret. Tokens are kept in `localStorage` in the SPA; for production consider an httpOnly-cookie flow.

## Run it

Prerequisites: Java 21, Maven, Node 20+, Docker, and an OpenAI API key.

```bash
# 1. Database (Postgres 17 + pgvector)
docker compose up -d

# 2. Backend  (http://localhost:8080)
cd backend
export OPENAI_API_KEY=sk-...
export JWT_SECRET="$(openssl rand -hex 32)"     # any string of 32+ chars
mvn spring-boot:run

# 3. Frontend (http://localhost:5173)
cd frontend
npm install
npm run dev
```

The Vite dev server proxies `/api` to the backend, so there is no CORS setup in development.

### Configuration (environment variables)

| Variable | Default | Purpose |
|---|---|---|
| `OPENAI_API_KEY` | required | Embeddings and chat |
| `CHAT_MODEL` | `gpt-4.1-mini` | Chat model name |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | Embedding model |
| `EMBEDDING_DIMENSIONS` | `1536` | Must match the `vector(...)` column in `V2` |
| `JWT_SECRET` | dev placeholder | **Set this in any real environment** |
| `DB_URL` / `DB_USER` / `DB_PASSWORD` | local docker values | Postgres connection |
| `STORAGE_DIR` | `./data/books` | Where uploaded PDFs are kept |
| `CORS_ORIGINS` | `http://localhost:5173` | Allowed browser origins |

RAG tuning lives under `bookwise.rag.*` in `application.yml` (`top-k`, `similarity-threshold`, `chunk-size-tokens`, `history-messages`).

### Using a different LLM provider

Swap the `spring-ai-starter-model-openai` dependency in `pom.xml` for another Spring AI model starter (Ollama, Google GenAI, and so on) and replace the `spring.ai.openai.*` properties. Anthropic's API has no embeddings endpoint, so pair a Claude chat model with a different embedding provider. If the embedding dimension changes, update the migration and re-index.

## API

All routes except register/login need `Authorization: Bearer <token>`. Errors are RFC 7807 `ProblemDetail` JSON; the UI shows `detail`.

| Method | Path | Notes |
|---|---|---|
| POST | `/api/auth/register`, `/api/auth/login` | Returns `{ token, user }` |
| GET | `/api/auth/me` | Current user |
| GET | `/api/books` | Your library |
| POST | `/api/books` | Multipart `file`; returns 202 while indexing continues |
| GET | `/api/books/{id}` | Poll `status`: `PROCESSING`, `READY`, `FAILED` |
| GET | `/api/books/{id}/file` | Original PDF (used to open a cited page) |
| DELETE | `/api/books/{id}` | Removes file, vectors and chat history |
| POST | `/api/books/{id}/chat` | `{ "question": "..." }` returns the answer with `citations[]` |
| GET / DELETE | `/api/books/{id}/messages` | Read / clear chat history |

## Known limits and next steps

- **No OCR:** scanned PDFs without selectable text fail with a clear message.
- **No streaming:** answers arrive in one response; SSE streaming is the natural next upgrade.
- **Follow-up questions** are answered with recent history in the prompt, but retrieval uses only the latest question. Adding a query-rewrite step would improve "what about the second one?" style questions.
- **Ingestion is in-process:** a restart marks in-flight books as failed (they must be re-uploaded). A job queue would fix this.
- **No rate limiting** on login or chat; add it before exposing this publicly.
- **Retrieval quality:** consider hybrid (keyword + vector) search and a re-ranker for large or technical books.
